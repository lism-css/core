# スクリーンショットからの Lism CSS ベース HTML 生成に関するアプローチ提案

> **前提の変更**（2026-07-03）: 本提案は当初「フレームワーク非依存の素の HTML/CSS 生成」を前提に書かれたが、[00-project-overview.md §3.3](./00-project-overview.md#33-lism-css-guide-の補助スキルとして-lism-css-出力を前提とする2026-07-03) の決定に伴い、**出力先を Lism CSS ベースの HTML** に変更した。以下、記述の意図が変わらない範囲で読み替えて解釈できるよう、要所を Lism 前提に修正してある。

## 質問の要約

LP などの 1 ページ構成の Web サイトを想定し、デザインのスクリーンショットを入力として忠実に **Lism CSS ベースの HTML** を生成する LLM の Skill（`screenshot-to-lism-html`、`lism-css-guide` の補助スキル）を作成するにあたり、以下の 2 点の懸念を解決する手法やアプローチについて。

1. **正確な読み取りと再現:** 画像からどのようにデザインを正確に読み取り、再現できるようにするか。
2. **不足情報の補完:** スクリーンショットのみでは分からない情報（レスポンシブ時の挙動など）について、意図を汲み取って組むにはどのようなアプローチを取るべきか。

---

## 回答内容（提案）

プロジェクトの先行研究ドキュメント（`01-prior-research-summary.md`）を拝見しました。

すでに「Figma MCP + Lism CSS」や「機械計測（Layout-first）」を用いた高度な検証を行われており、**「LLMはよくあるLPテンプレートに当てはめて推測でコーディングしてしまう（幻覚/ハルシネーション）」「VRT（Visual Regression Testing）やIoUだけではレイアウトの構造的欠陥を弾ききれない」**という本質的な課題にぶつかっていることがよく分かりました。

これらの先行研究の教訓を踏まえ、ご懸念の2点（正確な読み取りと、不足情報の補完）に対して、どのようなアプローチでLLM Skill（プロンプト・ワークフロー）を構築すべきか、私の意見を提案します。

### 1. 懸念1: 画像から正確にデザインを読み取り再現するには？

先行研究でHeroセクションの構造を誤認したように、現在のVLM（視覚言語モデル）にLP全体の長大な画像をそのまま渡して「HTMLを書いて」と指示すると、**画像の詳細な観察をサボり、学習データの『典型的なLPのコード』を出力してしまう**傾向があります。これを防ぐアプローチが必要です。

#### A. 全体画像ではなく「セクションごとの分割画像」で処理する
LP全体を1枚の画像として処理させるのはVLMにとって負荷が高く、細部（マージン、フォントの違い、重なり合い）を見落とします。
Skillのフローとして、**「1. ユーザーに画像をセクションごとに分割して入力してもらう（またはスクリプトで分割する）」** または **「2. まずLLMにセクション境界のY座標だけを推測させ、セクションごとにコーディングさせる」** アプローチを強く推奨します。
1セクションの画像だけであれば、VLMは「ここは背景写真の上にカードが3枚重なっている」といった詳細な構造を正確に読み取れる確率が跳ね上がります。

#### B. 「中間表現（抽象DOMツリー）」の生成を強制し、それを絶対の契約とする
先行研究の `design-inventory.md` のアプローチをさらに強固にします。
HTMLを書かせる前に、以下のような**「レイアウト構造のみのJSONまたはMarkdown（抽象DOMツリー）」**を生成させます。

```json
{
  "section": "Hero",
  "background": "image (overlay: rgba(0,0,0,0.4))",
  "layout": "stack (center aligned)",
  "elements": [
    { "type": "heading", "font-family": "serif", "text": "本物の家具を..." },
    { "type": "image_group", "layout": "overlap, 3 items" }
  ]
}
```
そして、コーディングフェーズのプロンプトで**「この中間表現の構造から1ミリも逸脱してはいけない。勝手に要素を足したり、よくあるLPの形に丸めないこと」**と強く制約をかけます。

#### C. Visual Critique（視覚的な自己検証）ループの導入
先行研究ではVRT（ピクセル単位の差分）やIoUを使っていましたが、数値だけでは「見た目は似ているがHTML構造が全く違う」ケースを防げません。
もし可能であれば、Skillの中で**「生成したHTMLのスクリーンショットをPuppeteer等で撮影し、元のデザイン画像と並べてVLM自身に入力し、『どこが違うか間違い探し』をさせる」**ループを組むのが有効です。「ボタンの余白が狭い」「見出しのフォントがセリフ体になっていない」など、VLMは「間違い探し」のタスクにおいては非常に高い精度を発揮します。

### 2. 懸念2: レスポンシブ等、不足している情報をどう補完するか？

スクリーンショットにない情報をLLMの「適当な推測」に任せると、プロジェクトごとに品質がブレてしまいます。ここには**「決定論的なルール（ヒューリスティクス）」**を持ち込む必要があります。

#### A. UIパターンカタログへの「レスポンシブ振る舞い」のハードコード
先行研究の `pattern-catalog.md` は素晴らしい資産です。本 Skill の `pattern-catalog.md` は「画像パターン → Lism プリミティブ」のマッピング表として再構成しており、レスポンシブ挙動の実装ルール自体は `lism-css-guide/responsive.md` に委譲します。ここで LLM に機械的に適用させたいのは、**「各画像パターンがモバイルになったときにどう変化すべきか（＝どの Lism プリミティブの Props / `_{bp}` サフィックスに落ちるか）」** です。

*例（Skill 内のルール定義）:*
- `equal-columns`（3 列カードなど）: `l--columns` にマップ。PC 3 列 → タブレット 2 列 → SP 1 列を Props で切替（`<Columns cols={[1, 2, 3]}>`。`gtc="repeat(3, 1fr)"` 直書きは NG）。
- `inline-row`（ヘッダーナビなど）: `l--cluster` にマップ。モバイルでは非表示にしてハンバーガーメニュー（`@lism-css/ui` の対応コンポーネント）に置き換える。

#### B. 実装前の「見えない仕様」の言語化フェーズ
コーディングをしながらレスポンシブやホバーを考えさせると、LLMのコンテキストが溢れてミスをします。
そのため、最初の設計フェーズで**「見えない仕様の策定」**を明示的に行わせます。

1. **ホバー推測**: 「このボタンの色は青だから、ホバー時は少し暗い青（`brightness(0.9)`など）になるはずだ」
2. **レスポンシブ推測**: 「この要素は `fluid-card-grid` パターンなので、モバイル時は1カラムに折り返そう」
これらを `spec.md` のようなテキストに一度出力させ、人間がそれをレビュー（必要なら修正）してから、HTML/CSS生成に進むというフローです。

### まとめ：推奨されるSkillのワークフロー（提案）

これらを踏まえると、本プロジェクトの Skill は以下のような段階的なアプローチを取るのが最も成功確率が高いと考えます。以下は初期提案時のフェーズ設計で、実装済みの現行ワークフローは [../SKILL.md](../SKILL.md) を参照してください（Phase 0: 画像分割 → 1: 抽象 DOM ツリー → 2: 骨格 HTML → 3: スタイリング → 4: Visual Critique の 5 フェーズ構成）。

1. **Phase 1: Design Analysis & Tokenization（画像分析と仕様化）**
   - 入力画像を渡し、全体の色・フォントルール・各セクションのパターン（`pattern-catalog.md` に基づく Lism プリミティブへのマッピング）を抽出させる。
   - 色・スペーシング・タイポの生値を記録し、後段で Lism トークンへ照合する（トークン照合ルールは `lism-css-guide/SKILL.md`）。
   - レスポンシブ時の挙動やホバーエフェクトの「仮説」をテキストで出力させる。
2. **Phase 2: Skeleton HTML（グレーボックス骨格構築）**
   - Property Class や装飾、実際の画像を当てる前に、Semantic な HTML と **Lism プリミティブのクラス名（`l--stack` / `l--columns` / `l--frame` / `is--container` 等）だけ**を持った骨格 HTML を組ませる。
   - *（ここで構造が「よくある LP」にハルシネーションしていないかチェックする）*
3. **Phase 3: Section-by-Section Styling（セクションごとの個別実装）**
   - LP 全体を一気にスタイリングさせず、「Hero セクションだけスタイリングして」「次は Features セクション」というように、**局所的にフォーカス**させて実装を進める。
   - Lism の Property Class（`-fz:*` / `-p:*` / `-bgc:*` / `-hov:*` 等）で書けるものはマークアップ側に寄せる。CSS に書くのは擬似クラス・状態切替など「CSS でしか書けない宣言」のみ（`lism-css-guide/SKILL.md` の「プリフライト・c-- 定義時の分解」）。
4. **Phase 4: Self-Correction（自己修正）**
   - 出来上がったものをレビューし、Phase 1 で定めた仕様（フォントがセリフ体である等）から逸脱がないかチェックさせる。あわせて `lism-css-guide/antipatterns.md` の NG パターン（Grid 直書きなど）を踏んでいないかも確認する。

先行研究の「画像を読み切る前にコードを書かせない」という思想は完全に正しいです。本プロジェクトでは、さらに **「LLM のテンプレート想起（幻覚）をどう抑制するか（＝抽象ツリーの強制とセクションごとの個別処理）」「見えない仕様をどうルール化するか（＝パターンへの振る舞い定義の追加）」** に注力して Skill を設計していくと、25% の壁を突破できるのではないかと考えています。Lism CSS 側の実装ルールは `lism-css-guide` に完全に委譲することで、本 Skill は「画像 → 構造の忠実さ」に一点集中できます。
