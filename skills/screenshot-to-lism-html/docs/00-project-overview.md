# プロジェクト概要

本プロジェクト（`screenshot-to-lism-html`）の目的・スコープ・決定事項を集約するドキュメント。
ブレインストーミングで合意した内容は本ファイルに追記していく。

> **位置づけ**: 本ファイルは「現時点での合意・決定」をまとめる場所。
> 先行研究の経緯・課題は [01-prior-research-summary.md](./01-prior-research-summary.md) を参照。
> 本ドキュメント群は Skill 本体（`../SKILL.md` ほか）と対で管理される。将来的には `lism-css` リポジトリ配下へ統合される想定。

---

## 1. プロジェクトの目的

**サイトデザインのスクリーンショット（画像）を入力に、Lism CSS を使ってそのデザインを忠実に再現した HTML を生成する** ための **LLM 用 Skill**（`screenshot-to-lism-html`）を作成する。

本 Skill は、[Lism CSS 公式スキル `lism-css-guide`](https://github.com/lism-css/lism-css/tree/main/skills/lism-css-guide) の**補助スキル**として位置づける。Lism CSS 側の実装ルール（記法・命名・トークン・アンチパターン等）は `lism-css-guide` に委譲し、本 Skill は **画像 → 抽象 DOM ツリー → Lism CSS プリミティブへのマッピング → セクション別コーディング → Visual Critique** というワークフロー制御に集中する。

将来的には本 Skill を [lism-css リポジトリ](https://github.com/lism-css/lism-css) 配下へ統合し、Lism CSS 利用者が共通に使える補助スキル群の 1 つとして提供する。

---

## 2. スコープ

### 対象

- **入力**: サイトデザインの**スクリーンショット（画像）**
- **出力**: **Lism CSS を使った HTML**（Lism のプリミティブ・Property Class・トークンに準拠。必要に応じてカスタム CSS）
- **対象サイト種別**: 静的な Web ページ（ランディングページ等）を主な検証対象とする
- **前提スキル**: 本 Skill は `lism-css-guide` と併用する（Lism CSS の実装ルールはそちらに委譲）

### 非対象（当面）

- Figma MCP 経由の入力（Figma を使わずスクリーンショットのみで完結させる）
- Lism CSS 以外の CSS フレームワーク（TailwindCSS 等）への出力
- JavaScript による動的挙動（インタラクション、状態管理 等）
- Lism CSS 自体の記法・命名規則・トークン設計の解説（`lism-css-guide` の責務）

## 3. 主要な決定事項

ブレストで合意した決定を時系列で記録する。**史実として順に残す**方針。方針転換の経緯を後から追跡できるよう、上書きせず追記していく。

### 3.1 出力先はフレームワーク非依存の HTML / CSS（2026-06-21）**[2026-07-03 に §3.3 で撤回]**

**決定**: 本プロジェクトの Skill が生成するコードは **フレームワーク非依存の素の HTML / CSS** とする。

**理由**:

- 最終ゴールは Lism CSS での再現だが、Lism CSS を出力先にすると **「Lism CSS のベストプラクティスをまとめた Skill 側の問題」と「スクリーンショット→HTML 変換の Skill 側の問題」の切り分けが難しくなる**
- 先行研究（`screenshot-to-lism-css-guide`, `layout-first-to-lism-css-guide`）でも、デザイン再現度の低さの主因が Lism 文法ミスではなく「画像→構造の読み取り」にあることが判明している（[01-prior-research-summary.md §4.2](./01-prior-research-summary.md#42-screenshot-to-lism-css-guide-で観測された主因)）
- フレームワーク非依存に絞ることで、**スクリーンショット→デザイン忠実再現** という核心の課題に集中できる

**影響**:

- Lism CSS への接続は本プロジェクト完了後の別ステップ（最終ゴール側）で検討する
- 先行研究の資産の流用方針は §3.2 で別途決定

> **後日補足（2026-07-03）**: §3.3 で「`lism-css-guide` の補助スキルとして Lism CSS 出力を前提とする」方針に変更した。切り分けの懸念は、**Lism 実装ルールの責務を `lism-css-guide` に委譲する**ことで解消する運用にした（本 Skill は画像 → 構造の読み取りとプリミティブへのマッピングのみを担当）。

### 3.2 先行研究はゼロから設計し直す前提で参考扱い（2026-06-21）

**決定**: 先行研究の Skill 群（`screenshot-to-lism-css-guide` / `layout-first-to-lism-css-guide`）の構造・ファイル分割をそのまま引き継がず、**ゼロから設計する**。先行研究で実証された有効なアプローチは、本プロジェクトの設計を進める中で**必要になったタイミングで個別に取り入れる**。

**理由**:

- 先行研究の Skill は構造的欠陥を抱えていた（IoU トートロジー、グレーボックス工程の欠落 など、[01 §4.3](./01-prior-research-summary.md#43-layout-first-to-lism-css-guide-で観測された主因)）
- 既存スキルの構造を起点に「修正」する形だと、これらの欠陥や設計上の前提を無自覚に継承するリスクがある
- 先行研究の補助ドキュメントは充実しているが、**それでも構造誤認は防げなかった**（[01 §4.2](./01-prior-research-summary.md#42-screenshot-to-lism-css-guide-で観測された主因)）。資産流用ありきの設計だと根本的なアプローチ転換が難しくなる

**運用ルール**:

- 先行研究の特定資産（`pattern-catalog.md` 等）の流用判断は、**そのトピックを実際に設計するタイミング**で行う
- 流用する場合も、本プロジェクトの設計意図に合わせて再構成する（コピペでの取り込みはしない）
- 先行研究で「効かなかった」と判明したアプローチ（補助 md 充実だけで構造誤認を防ぐ等）は安易に踏襲しない

### 3.3 `lism-css-guide` の補助スキルとして Lism CSS 出力を前提とする（2026-07-03）

**決定**: 本 Skill を **[`lism-css-guide`](https://github.com/lism-css/lism-css/tree/main/skills/lism-css-guide) の補助スキル**として再構成し、出力先を **Lism CSS を使った HTML** とする。ディレクトリ名・Skill 名も改名する。

- Skill 名: `Screenshot to HTML (Plain)` → **`Screenshot to Lism HTML`**
- ディレクトリ: `.cursor/skills/screenshot-to-html/` → `.cursor/skills/screenshot-to-lism-html/`
- SKILL.md に YAML フロントマター（`name` / `description`）を追加
- 将来的に [lism-css リポジトリ](https://github.com/lism-css/lism-css) 配下（`skills/screenshot-to-lism-html/`）へ統合する前提で整理する

**理由**:

- §3.1 の懸念（「Lism CSS 側の問題」と「画像 → 構造読み取り側の問題」の切り分け困難）は、**責務分担を明示することで解消可能**と判断した：
  - **本 Skill**: 画像 → 抽象 DOM ツリー → Lism プリミティブへの**マッピング**まで
  - **`lism-css-guide`**: Lism CSS の記法・命名・トークン・アンチパターンなど**実装ルール**
- スキル完成度としてはまだ課題が多い状態だが、**先に「Lism CSS 補助スキルとしての位置づけ」を整えて lism-css リポジトリ側の設計にも影響を反映できる状態を作る**ことを優先する
- Skill の完成度改善（読み取り精度向上・検証指標設計など §5 の論点）は、位置づけ整理と並行して進める

**運用ルール**:

- 本 Skill の資材（`pattern-catalog.md` 等）は **Lism 記法の詳細を書かない**。「画像パターン → Lism プリミティブ」のマッピングに徹し、Lism の記法・トークン値・命名規則は `lism-css-guide` を参照させる
- Phase 3（スタイリング）ではデザイン画像の生値と Lism トークンを照合し、`lism-css-guide` の「デザインデータ取り込み時のフロー」（A: px 直書き / B: 最寄りトークン / C: 基準値上書き）でユーザーに方針を確認してから実装する
- Skill 内資材の詳細変更ログは、必要に応じて別ドキュメントに切り出す（本ファイルは決定事項の要約のみ）

**影響**:

- 本ファイル §1〜2（目的・スコープ）を Lism CSS 前提に書き換え済み
- 関連ドキュメント（03-usage-prompt-examples.md、04-how-it-works.md）を Lism CSS 前提に修正
- ドキュメント群を `docs/` から `.cursor/skills/screenshot-to-lism-html/docs/` へ移動（Skill と対で管理）

## 4. ブレスト記録

### 4.1 読み取りミスの根本原因の分類（2026-06-21）

先行研究の Interior LP 検証で観測された構造誤認（Hero / Step / ナビ文言 等）の原因を 3 軸で分類。

#### A. モデル側の認知バイアス（LLM 由来）

| 原因 | メカニズム | 先行研究での現れ |
|------|-----------|-----------------|
| A1. テンプレート想起 | 学習済みの「典型 LP」prior で曖昧な画像を穴埋め | Hero を「コラージュ型」と認識できず「全面背景+暗いオーバーレイ」に置換 |
| A2. 出力先行バイアス | 「HTML を書く」task framing が読み取りを浅くする | 「インベントリ完成まで HTML 書かない」プロンプトでも完全には防げず |
| A3. 抽象化への引力 | 「カテゴリで理解する」傾向が固有の詳細を捨てる | Step を「左右交互の写真群」ではなく「左 1 枚 + 右にリスト」に簡略化 |
| A4. パターン語彙の自己強化 | パターン定義語彙が「必ずどれかに当てはめる」モードを誘発 | confusion-pairs を整備しても CP-01 誤判定が起きる |

#### B. 入力情報の損失（マルチモーダル処理由来）

| 原因 | メカニズム |
|------|-----------|
| B1. トークン化での解像度低下 | 画像は固定タイル/解像度に圧縮され細部が潰れる |
| B2. 縦長画像の空間圧縮 | LP は縦長（例: 8273px）。1 画像で渡すと縦方向密度が極端に低下 |
| B3. 高周波情報の欠落 | 写真境界・スクリム・微小余白がダウンサンプルで判別困難 |
| B4. 文言の OCR 精度 | LLM ビジョンは OCR 特化ではなく文言読み取りに失敗・幻覚 |

#### C. 検証の不在（ワークフロー由来）

| 原因 | メカニズム | 先行研究での現れ |
|------|-----------|-----------------|
| C1. 読み取りが暗黙的 | LLM が「何をどう読み取ったか」が記録されず修正点を特定不能 | design-inventory はあるが画像との突合は手動 |
| C2. エラーの伝搬 | セクション境界誤推定が以降全工程を汚染 | sections.json の境界が prior として汚染 |
| C3. 検証指標のミスマッチ | IoU（位置）も pixel diff（見た目）も「構造の正しさ」を測れない | layout-first は IoU 1.0 で合格してもデザインと乖離 |
| C4. ユーザー確認ポイント欠如 | 全自動で走るため初期の構造誤認が出力直前まで気づかれない | 30% の不一致が出てから手戻り |

**因果構造**: 「A モデルの誤読」×「B 入力損失」×「C 検証不在」が複合して 30% の壁を作っている。

### 4.2 有効そうなアプローチ案（2026-06-21）

各案がどの原因（A/B/C）を攻撃するかを明示。★=先行研究にあった案、☆=新規提案。

> **§3.3 決定後の補足（2026-07-03）**: 出力先を Lism CSS に確定させたことで、以下のアプローチはすべて **「画像から Lism プリミティブ／トークン／Property Class への正確なマッピング」** を最終ゴールとして評価する。Lism 記法上の妥当性チェックは `lism-css-guide` 側で担保されるため、本 Skill の検証設計は「構造の忠実さ」に一段集中しやすくなった。

#### I. 入力情報の損失対策（B 系）

| # | アプローチ | 内容 | 攻撃対象 |
|---|-----------|------|---------|
| 1 ☆ | マルチスケール入力 | 全体縮小版＋セクションごと高解像度クロップを複数画像で LLM に渡す | B1, B2 |
| 2 ☆ | 注釈オーバーレイ自動生成 | 背景色変化からセクション境界をスクリプト検出し、境界線・番号を描いた注釈画像を生成 → LLM はそれを見る | B2, C2 |
| 3 ☆ | OCR グラウンディング | Tesseract / Cloud Vision で文言＋bounding box を抽出して JSON で LLM に与える。文言読み取りを LLM から切り離す | B4 |
| 4 ☆ | 要素検出による前処理 | 写真領域・テキスト塊・カードを CV モデルで検出し bbox を LLM に渡す | B3 |
| 5 ★ | 計測ファースト（layout-spec.json） | 先行研究手法。IoU トートロジー対策が別途必要 | B3 |

#### II. モデルの認知バイアス対策（A 系）

| # | アプローチ | 内容 | 攻撃対象 |
|---|-----------|------|---------|
| 6 ☆ | 「不明」を許容する強制選択 | パターン分類で「該当なし / 確信度低」を正式な選択肢にし、選択時はユーザー確認に分岐 | A1, A4 |
| 7 ☆ | 詳細記述ゲート | HTML 着手前に「写真は何枚？重なっているか？オーバーレイは？」等を質問形式で逐一答えさせる | A3, C1 |
| 8 ☆ | few-shot による混同ペア提示 | confusion-pairs の各ペアの実例画像＋正解 HTML を few-shot で渡す | A1 |
| 9 ★ | 「テンプレ当てはめ禁止」プロンプト | 先行研究で実施済み。単独効果限定的、他と組み合わせ前提 | A1 |

#### III. 検証と修正ループ（C 系）

| # | アプローチ | 内容 | 攻撃対象 |
|---|-----------|------|---------|
| 10 ☆ | セルフレンダリング照合ループ | 1 セクション実装→Playwright で当該セクション撮影→入力クロップと並べて LLM が差分指摘→修正、を反復。VRT を生成ループ内に組み込む | C1, C2, C3 |
| 11 ☆ | 段階的ユーザー確認 | 節目（境界確定後/インベントリ完成後/セクション完成後）で UI 上にユーザー確認を出す | C2, C4 |

#### 組み合わせ候補（叩き台）

| パターン | 構成 | 特徴 |
|---------|------|------|
| X. 前処理で殺す | 1 + 2 + 3 | LLM の負荷を「構造解釈」だけに絞る。実装コスト高 |
| Y. ループで詰める | 7 + 10 + 11 | LLM 認知強化＋頻繁な検証。ユーザー負荷高 |
| Z. ハイブリッド | 1 + 2 + 7 + 10 | 全方位カバー。複雑だがユーザー負荷は控えめ |
