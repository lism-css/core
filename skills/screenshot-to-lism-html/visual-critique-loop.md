# Visual Critique (自己検証) と修正ループ

このドキュメントは、生成されたHTML/CSSの見た目が、元のデザイン画像と一致しているかをLLM自身に視覚的に検証させ、修正を促すためのワークフローです。
このループは、デザインと実装の差異（差分）が許容範囲内に収まるまで繰り返されます。

## 前提作業 (スクリプトの実行)

LLM（あなた）は、Terminalツールを使用して以下のコマンドを実行し、プレビュー画像を生成します。
`<skill-dir>` は本スキルのディレクトリです（SKILL.md の「事前準備」を参照）。プロジェクトルートから実行し、パスはカレントディレクトリ基準で指定します。
（HTMLのファイルパスが `output/index.html` の場合）

```bash
node <skill-dir>/scripts/capture_preview.js output/index.html output/preview.png
```

## プロンプト指示: 間違い探しと修正 (Visual Critique)

**ユーザー（またはシステム）からの入力:**
1. 元のデザイン画像 (`reference.jpg`) または 元のセクション画像群
2. スクリプトで撮影したプレビュー画像 (`preview.png`)

**LLMへのプロンプト指示:**
> あなたは非常に厳格なQAエンジニア・デザイナーです。
> 元のデザイン画像と、あなたが生成したHTMLのプレビュー画像を比較し、「間違い探し」を行ってください。
> 以下の観点で厳密にチェックし、ズレている部分をリストアップしてください。
> 
> **チェック観点:**
> 1. **タイポグラフィ**: フォントファミリー（明朝体/ゴシック体の違い）、フォントサイズ、文字色、行間（line-height）、文字間隔（letter-spacing）。Lism の `--fz--*` / `--lh--*` トークンへの寄せ具合も併せて確認。
> 2. **スペーシング**: 要素間の余白（margin, padding）、画像とテキストの距離、セクション間の空白。Lism の spacing トークン（`--s*`）からズレていないか。
> 3. **レイアウトと配置**: 要素の配置（中央揃え、左揃え）、カラムの幅の比率、要素の重なり合い、はみ出し。使っているプリミティブ（`l--columns` / `l--withSide` / `l--frame` 等）の選定が妥当かも合わせて評価。
> 4. **色と装飾**: 背景色、ボタンの色、ボーダーの太さと色、角丸（border-radius）、影（box-shadow）、オーバーレイの濃さ。Lism のカラートークン・角丸トークン（`--bdrs--*`）・影トークン（`--bxsh--*`）を使用しているか。
> 
> **出力フォーマット:**
> ```markdown
> ### 差分レポート
> 
> - [ ] Heroセクションのメイン見出しのフォントがセリフ体（明朝体）になっておらず、サンセリフ体になっている。
> - [ ] Featuresセクションの3列カード間の余白（gap）が、デザインよりも狭い。
> - [ ] Contactボタンの背景色が、デザインのPrimary Color（`--keycolor`）よりも少し暗い。
> - [ ] 画像上の黒いオーバーレイが濃すぎで、テキストが沈んで見える。
> - [ ] Featuresセクションを `<Grid gtc="repeat(3, 1fr)">` で組んでいるが、レスポンシブでカラム数が切り替わらない。`<Columns cols={[1, 2, 3]}>` に書き換える必要がある。
> ```
> 
> 指摘事項をリストアップしたら、その指摘を修正するための Lism CSS の Property Class（必要に応じてカスタム CSS ／ HTML）の変更コードを出力し、ファイルを更新してください。修正時も `lism-css-guide` のルール（プリミティブ選定・トークン照合・c-- 分解）に従い、`antipatterns.md` の NG を踏まないこと。
> 変更後、再度プレビュースクリプトを実行して修正が反映されたか確認します。
> 
> **終了条件:**
> 明らかなレイアウト崩れやフォントの不一致がなくなり、全体的な印象が元のデザインと見分けがつかなくなった時点でループを終了し、作業完了を報告してください。（最大3回までループ）
